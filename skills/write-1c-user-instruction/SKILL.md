# Подробная ERP-инструкция

## Допуск

1. Проверить `approval_status: approved` у требований и проекта со схемой; при отсутствии апрува или расхождении версий остановиться.
2. Проверить продукт и релиз. XML допустим только при точном совпадении; для остальных конфигураций использовать документацию и разрешённый веб-поиск с явным предупреждением.

## Формирование

1. Сохранить идентификаторы шагов P01, P02 и далее из утверждённой схемы.
2. Для каждого шага указать роль, предусловие, полный путь по интерфейсу, команду, форму, поля и значения, действие записи/проведения, ожидаемый статус, результат и способ проверки.
3. Разделять настройку системы, подготовку НСИ, ежедневную операцию, контроль и исправление.
4. Для точных имён указывать доказательство: ИТС, metadata XML с путём к файлу или проверка в целевой базе.
5. Не выводить пользовательский путь только из имени объекта метаданных. Подтвердить размещение команды в подсистеме или интерфейсе.
6. Если подпись не подтверждена, не использовать неструктурированный placeholder. Создать блок `⚠ Не подтверждено` со статусом `needs_review`, перечнем проверенных источников и ручной проверкой.
7. Описать частичное исполнение, отмену, возврат на доработку и безопасное исправление.
8. Завершить контрольным сценарием по тем же шагам схемы.

## Компактность

1. Начать с короткой карты этапов и ролей.
2. Одно пользовательское действие оформлять одним нумерованным шагом.
3. Повторяющиеся поля выносить в таблицу, не повторять одинаковые пояснения.
4. В основной текст включать только обязательные действия и проверки; редкие исключения выносить в отдельный раздел.
5. Не показывать пользователю внутренние имена метаданных, UUID и XML-пути. Хранить их в колонке источника или техническом приложении.
6. Не пересказывать устройство 1С, если оно не влияет на действие пользователя.

Формат действия: PNN. Роль. Раздел → группа → команда. Открыть форму. Заполнить поля. Выполнить команду. Ожидаемый статус. Результат. Проверка. Источник.

## Аудит качества

1. Перед доработкой перечислить все placeholders, неподтверждённые поля, статусы, команды, пути и незамкнутые ветки.
2. Для каждого шага хранить машинно-читаемые `step_id`, `roles` и `evidence` в HTML-комментарии.
3. Использовать evidence: `verified_its`, `verified_metadata`, `verified_both`, `project_decision`, `local_regulation`, `needs_review`.
4. Сохранить master-файл единым; ролевые инструкции получать фильтрацией `roles`, не копированием текста.
5. Для оставшихся неопределённостей создать отдельные `NR-xx` и указать, что проверено и что требуется проверить вручную.
6. Создать рядом `<instruction-name>-validation.md` со счётчиками, оставшимися `needs_review` и заключением о готовности.
7. Выполнить `python scripts/validate_instruction.py <instruction.md>`. Статус `verified` допустим только без ошибок и `needs_review`.

## Обратная связь и статус

1. Сохранить новый результат как `approval_status: pending_approval` и `review_status: feedback_pending`.
2. После показа спросить: «Всё ли устраивает?».
3. Только при явном подтверждении установить `approval_status: approved`, `review_status: successful` и разрешить использовать инструкцию как совместимый пример.
4. При замечании установить `review_status: needs_revision`, сохранить причину и создать следующую версию.
5. Если замечание поступило после подтверждения, отозвать апрув и исключить прежнюю версию из успешных примеров.
