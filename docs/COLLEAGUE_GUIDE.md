# Руководство для коллег

## Что запускается

Откройте NewAgent в Codex/OpenCode либо запустите `start_erp_pi.cmd`. Интерфейс
вызывает `consultant.cmd`; Python выполняет lifecycle, hybrid graph search,
сохранение и проверки, а смысловые этапы отправляет на Wormsoft API-роли low/medium/high.

Python перед каждым API-вызовом читает координирующий скилл
`skills/prepare-1c-consulting-answer/SKILL.md`, общую modeling policy и профильный
скилл роли: `analyze-1c-requirements`, `design-1c-process` или
`write-1c-user-instruction`. Pi, Codex и OpenCode не исполняют предметную генерацию
собственными моделями.

Сначала проверьте:

```powershell
consultant.cmd --repo . --json runtime-status
```

Команда показывает только факт настройки ключа и модели, но не секрет.

## Полный цикл

1. Создайте проект через меню или `new`. По умолчанию проект имеет единый формат
   `hybrid`: сквозной процесс плюс подробная инструкция консультанта.
2. Выполните `preflight`: локальный source routing, аналитика, граф и Modeler без LLM.
3. `run` вызывает translator/low и сохраняет пакет вопросов.
4. Запишите ответы, затем отдельно утвердите требования.
5. `run` вызывает planner/medium и сохраняет проект решения. Проверьте основную
   цепочку документов, параллельные/альтернативные ветви, GAP и критерии приёмки.
6. Отдельно утвердите design.
7. `run` вызывает writer/high, сохраняет draft и выполняет Modeler.
8. Покажите файл из `answers_md` и спросите: «Всё ли устраивает?».
9. Только явное подтверждение записывается как instruction approval.

## Вопросы проекту

`ask <id> "<вопрос>" --kind process|consultant|vanessa|implementation` формирует
сохранённый Markdown, не меняя lifecycle и approvals. Повтор идентичного вопроса в
той же ревизии использует готовый файл без нового API-вызова.

Формат выбирается именно здесь: один и тот же сохранённый проект можно исследовать
как процесс, запросить маршрут «куда нажимать», сценарий Vanessa или рекомендации
по реализации.

## Ревизии

Изменение ответа, контекста или замечание отзывает затронутые approvals. Предыдущие
файлы остаются в `revisions/`, успешный пример исключается из индекса. Используйте
`decision`, `revise-design` и `request-changes`, а не ручную правку project state.

## Где лежат данные

```text
results/<project-id>/
├── project.yaml
├── 01-requirements.md
├── 02-design.md
├── 03-instruction.md
├── analysis/
├── agent_artifacts/
├── answers_md/
├── revisions/
└── events.ndjson
```

`agent_artifacts/graph-context-rNNN.json` содержит компактные результаты hybrid
search, node/edge IDs и source_ref. Для каждого AI-вызова там же сохраняются точный
`*-prompt.txt` и `*-execution.json`. Итоговый Markdown содержит ссылку на prompt,
модель, входные, cached, выходные, reasoning и суммарные токены. `answers_md/`
содержит версии инструкции и ответы на дополнительные вопросы.

## Pi

Запустите `start_erp_pi.cmd`, затем введите `/erp`. После выбора существующего
проекта меню показывает только действия, допустимые в его текущем статусе.

Для нового проекта последовательность такая:

1. Выберите `＋ Новый проект`, укажите название и источник ТЗ: загрузить `.md` по
   полному пути либо вставить текст. Затем укажите точный релиз. Проект автоматически
   создаётся в формате `hybrid`; загруженный оригинал сохраняется как `00-source.md`.
2. Выберите `Предварительная проверка без LLM`. Она создаёт/обновляет локальную
   аналитическую модель, маршрутизирует источники и готовит контекст графа. Для
   старого проекта без `analysis.json` модель создаётся автоматически из
   `00-request.md`; API не вызывается.
3. Выберите `Сформировать пакет вопросов · translator/low`. Только теперь появляется
   пункт `Ответить на сформированные вопросы`.
4. Проверьте в `01-requirements.md` аудит числа требований, кластеров и локальных
   сигналов неопределённости. Ответьте на все вопросы, затем отдельно выберите
   `Утвердить требования`; повторно вводить слово «утвердить» не требуется.
5. Выберите `Сформировать проект решения · planner/medium`. Проверьте начинающую
   документ цепочку, альтернативные и параллельные ветви, GAP и тесты.
6. Выберите `Утвердить проект решения` либо верните design на доработку.
7. Выберите `Сформировать итоговый ответ · writer/high`. Markdown сохраняется в
   `results/<project-id>/answers_md/`, затем локально выполняются контракт и Modeler.
8. Прочитайте результат и выберите `Подтвердить итог: всё устраивает` либо
   `Отправить итог на доработку`. Только первый вариант переводит проект в
   `successful`.

Пункт `Задать отдельный вопрос проекту` доступен независимо от основного lifecycle.
Выберите вид ответа: описание процесса, инструкция консультанта, Vanessa или вопрос
по реализации. Ответ также сохраняется в `answers_md`; одинаковый вопрос в той же
ревизии повторно API не вызывает.

Сообщение `Пакет вопросов ещё не сформирован` означает, что был пропущен шаг 3.
Сообщение `Аналитическая модель не найдена` относится к legacy-проекту; обновлённый
runtime устраняет его бесплатной автоинициализацией на шаге 2.

## Диагностика

- ключ не найден: задайте `NEWAGENT_API_KEY`/`WORMSOFT_API_KEY` либо оставьте
  существующий ключ в разрешённом локальном `.env`;
- граф не найден: проверьте наличие опубликованного sidecar в `../RAGAgent/graph_rag_data`;
- Modeler требует review: точный релиз или путь не подтверждён; такой шаг нельзя
  переводить в successful;
- не удаётся продолжить этап: проверьте `status <project-id>` и требуемый approval.
