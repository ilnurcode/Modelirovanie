# Контракт четырёхслойного ERP-графа

## Слои

| Слой | Смысл | Применение |
|---|---|---|
| L1 | бизнес-сценарии | найти точку входа процесса |
| L2 | типовые уточнения | обнаружить ось бизнес-решения; не копировать вопрос автоматически |
| L3 | метаданные и UI | подтвердить объект, поле, форму, команду, регистр и техническую связь |
| L4 | знания ИТС | подтвердить назначение, порядок действий, варианты и ограничения |

## Основные связи

- `entry_doc`: сценарий → входной документ.
- `clarification`: сценарий → потенциальная ось уточнения.
- `clarifies_field`: уточнение → поле метаданных.
- `parent_child` / `child_parent`: иерархия знаний и объектов.
- `references`: смысловая или техническая ссылка.
- `has_field` / `field_of`: объект ↔ поле.
- `required_reference` / `required_by_field`: обязательная ссылка поля.
- `creates_on_basis` / `can_be_created_on_basis_of`: ввод на основании.
- `may_write_register` / `has_registrator`: документ ↔ регистр.
- `has_command` / `opened_by_command`: команда интерфейса ↔ объект.
- `in_subsystem` / `contains_object`: подсистема ↔ объект.
- `requires` / `required_by`: типизированная зависимость.
- `describes_metadata` / `documented_by`: доказательная связь раздела ИТС L4 с точным объектом L3. Проверять `evidence.method`, `matched_text`, `source_path`, `rule_version` и `confidence`.
- `shared_terms`: слабый сигнал; использовать только для расширения кандидатов.

## Идентификаторы и поиск

- `id` сохраняет совместимость с опубликованными legacy-ссылками.
- `canonical_id` — стабильный ID вида `onec:1c-erp:2.5:idv1:lN:<hash>`; версия схемы находится в `id_schema_version`.
- `content_version` меняется при изменении содержимого узла, не меняя его canonical ID.
- `search_nodes(mode="hybrid")` объединяет FTS5 и разреженный semantic index, затем применяет небольшой детерминированный reranker. `channels`, `lexical_rank`, `semantic_rank` и `rerank_score` объясняют попадание кандидата.

## Эвристика обхода

1. Найти L1/L4 по формулировке бизнеса.
2. Найти точные L3-объекты отдельным запросом.
3. Расширить выбранные узлы по типизированным связям.
4. Проверить доказательное L3↔L4-ребро и L4-источник для пользовательского смысла.
5. Сохранить точные ID и направления рёбер в карте доказательств.

Не использовать `shared_terms` как единственное доказательство. Не считать отсутствие ребра доказательством отсутствия функции: опубликованный граф может быть неполон.
