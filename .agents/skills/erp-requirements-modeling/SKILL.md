# ERP Requirements Modeling v4

Codex является только интерфейсом. Смысловую нормализацию и сопоставление выполняют API-агенты проекта через MCP `run_api_agent`; Codex не создаёт requirement-map, evidence-map, вопросы, solution-model, GAP, traceability, acceptance-tests или quality-gate своим ответом. MCP остаётся единым runtime и хранилищем графа, проектов и файлов.

Для первичного этапа вызвать `run_api_agent(role="erp-translator")`. После записи явных ответов пользователя и requirements approval вызвать `run_api_agent(role="erp-process-planner")`. Инструмент сам выбирает модель по `agent-runtime-policy.json`, формирует ограниченный контекст графа, запускает journal/provenance, сохраняет обязательные артефакты и записывает точные токены API. Не дублировать его работу через `start_agent_run`, `save_artifact` или `record_model_call_telemetry`.

## Телеметрия вопроса

Для существующего `project_id` первым MCP-вызовом сделать `start_project_query`; для нового проекта — сразу после `create_project`. Сохранить `query_id`, передать его в `run_api_agent` и перед передачей управления пользователю вызвать `finish_project_query`. `run_api_agent` сам записывает точный usage API-провайдера; не вызывать `record_model_call_telemetry` повторно.

## Создание или продолжение проекта

1. Получить текст ТЗ. Для файла сначала прочитать его подходящим инструментом формата; не просить пользователя вручную копировать доступный файл.
2. Вызвать `list_projects` и избежать случайного дубля.
3. Для нового проекта вызвать `create_project` с исходным текстом без эвристического переписывания, а также точными `product` и `release`. Для существующего — `get_project`.
4. Вызвать `get_api_agent_status`; если ключ не настроен, остановиться без авторской генерации и сообщить только ожидаемое имя переменной/`.env`.
5. Проверить `graph_status`, затем вызвать соответствующую роль через `run_api_agent`, передав `query_id` текущего вопроса.

## Модель требований

Получить от `erp-translator` атомарную карту требований. Для каждого требования агент должен зафиксировать:

- стабильный `requirement_id`;
- исходный фрагмент и краткую нормализованную формулировку;
- бизнес-цель, роль, триггер, вход, выход;
- основной поток, варианты, исключения и контроль;
- затронутые требования и решения;
- ERP-кандидаты и подтверждённые узлы отдельно;
- критерий приёмки;
- открытые вопросы.

Дополнительно хранить `cluster`, `coverage_status=covered|partial|gap`, `evidence_ids`, `solution_element_ids` и `acceptance_test_ids`. Стабильный ID строить из нормализованного исходного фрагмента и не менять при редакционной правке формулировки.

`run_api_agent` сохраняет карту и остальные артефакты автоматически. Codex только читает их и показывает пользователю.

## Итерационный цикл моделирования

1. Сгруппировать требования в смысловые кластеры, не по размеру файла.
2. Исследовать каждый кластер пакетно несколькими узкими `search_nodes(mode="hybrid")` и доказательными обходами графа. Повторно использовать найденные узлы; не запускать отдельный широкий поиск на каждое требование. Для L3↔L4 использовать `describes_metadata` / `documented_by` с сохранённым evidence ребра.
3. Сохранить `evidence-map` со статусами только `verified_source`, `verified_metadata`, `user_decision`, `candidate`, `unresolved`. Дедуплицировать по product + release + source_ref + intent.
4. Сформировать вопросы только там, где ответ пользователя меняет модель процесса, данные, ответственность, вариант учёта или критерий приёмки.
5. Показать один основной пакет максимум из 12 вопросов, сгруппированных по кластерам. Допустим только один точечный дополнительный вопрос при неоднозначном ответе.
6. Записывать только фактически полученные ответы через `record_decisions`, передавая `question_id`, точный `answer`, `normalized_value`, `allowed_values` и `affected_requirement_ids`. Не записывать модельное предположение как ответ пользователя. Если требуется вариант 1/2, ответ «подтверждаю настройки» не является выбором и не записывается.
7. После ответов пересмотреть только `affected_requirement_ids` и затронутые кластеры.

Не задавать пользователю вопросы вида «какой объект ERP выбрать», если это можно установить исследованием графа. Неполный маппинг оформлять как `gap`, а не как фиктивное бизнес-уточнение.

## Изменения и корректировки

- Новые условия сохранять через `add_project_context(mode="supplement")`.
- Опровержение старого контекста сохранять через `mode="correction"` и явно перечислять `supersedes_ids`, если они известны.
- Изменённый ответ записывать тем же `decision.id`: MCP сохранит предыдущую версию в истории.
- После любого изменения считать прежнее подтверждение снятым и пересобрать только затронутые смысловые артефакты.

## Артефакты перед подтверждением

Собрать и сохранить:

1. `solution-model` — ветвящаяся модель процесса с условиями, ролями, документами, данными и контролями.
2. `traceability` — каждое требование → решение пользователя → ERP-узлы/рёбра → элемент модели → критерий приёмки.
3. `gap-register` — технические GAP и отсутствующие данные заказчика. Critical GAP блокирует successful, пока не закрыт или явно не исключён пользователем.
4. `acceptance-tests` — предусловия, действия и ожидаемый результат; каждое covered-требование имеет хотя бы один тест.
5. `quality-gate` — структурированная самопроверка полноты и доказательности с `ready_for_design_approval`.

Использовать схемы из [artifact-contracts.md](references/artifact-contracts.md). Не подменять `quality-gate` повторным LLM-верификатором: это прозрачный артефакт текущего автора с перечисленными пробелами.

## Подтверждение

Вызвать `validate_project(for_final=false)` и исправить детерминированные ошибки. Показать пользователю краткую модель, ключевые ветви, решения, кандидаты и пробелы. Спросить явное подтверждение текущей ревизии. Только после ответа:

- при подтверждении вызвать `record_project_approval(stage="design", approved=true)`;
- при замечаниях вызвать `record_project_approval(stage="design", approved=false)`, записать изменения и повторить затронутый цикл.

Не вызывать `save_artifact(kind="answer")` в этом skill.

Целевой бюджет проекта — до 30 завершённых модельных вызовов. Превышение объяснять, но не считать автоматической ошибкой.

Перед передачей управления пользователю закрыть вопрос через `finish_project_query`: `needs_input`, если ожидаются ответы или подтверждение; `completed`, если моделирование текущего запроса закончено; `failed`, если нарушен контракт индекса или model policy. Агентный журнал уже закрыт `run_api_agent`; не вызывать `finish_agent_run` повторно. Все MCP-вызовы, выбранные узлы, артефакты, ревизии, время и точные API-токены остаются в журналах проекта.
