# ERP Solution Authoring v4

Codex является только интерфейсом. Итоговый ответ из подтверждённой модели и доказательств графа создаёт API-агент проекта `instruction-writer` через MCP `run_api_agent`. Не писать инструкцию моделью Codex и не запускать длинный цикл авторов и критиков; независимую проверку выполняет детерминированный `validate_project`.

## Телеметрия вопроса

Первым MCP-вызовом сделать `start_project_query` и сохранить `query_id`, затем передать его в `run_api_agent`. После сохранения Markdown и проверки вызвать `finish_project_query`, передав `answer_path`; при остановке или ошибке всё равно закрыть вопрос соответствующим статусом. `run_api_agent` сам записывает точный usage API-провайдера; не вызывать `record_model_call_telemetry` повторно.

## Входной контроль

1. Вызвать `get_project`.
2. Убедиться, что `approval_state.design == true`. Иначе остановиться и передать проект в `$erp-requirements-modeling`.
3. Вызвать `get_api_agent_status`; если ключ не настроен, остановиться без авторской генерации.
4. Вызвать `run_api_agent(role="instruction-writer", query_id=<текущий query_id>)`. Инструмент сам загрузит последние `requirement-map`, `evidence-map`, `decision-register`, `solution-model`, `gap-register`, `traceability`, `acceptance-tests` и `quality-gate`, запустит API и сохранит ответ.
5. Проверить, что quality gate относится к актуальной моделируемой ревизии и явно перечисляет оставшиеся пробелы.
6. При необходимости точечной проверки точного имени вызвать `get_nodes`, `expand_graph` по доказательным L3↔L4-рёбрам или `read_source`; не запускать новый широкий препроцесс.

## Структура ответа

Начинать с визуальной модели, затем давать текст:

1. локальное дерево документов и ключевых НСИ;
2. ветвящаяся Mermaid-карта процесса;
3. таблица решений и условий ветвления;
4. несколько маршрутных последовательностей для основных вариантов;
5. пошаговая инструкция: роль → предусловие → раздел/команда → форма/документ → реквизиты → действия → ожидаемый статус → результат → контроль;
6. исключения, возвраты, исправления и точки ручного решения;
7. проверки результата и критерии приёмки;
8. трассировка требований и честно обозначенные пробелы.

Один пользовательский шаг должен отражать реальную операцию в 1С и может покрывать несколько требований. Запрещено механически превращать каждое предложение ТЗ в отдельный шаг. Для каждого подтверждённого шага сохранять `step_id`, `requirement_ids`, `role`, `ui_path`, `form`, `fields`, `command`, `actions`, `expected_status`, `verification`, `verification_status`, `evidence_refs` и `semantic_relation_refs`.

Для плана внедрения дополнительно включать зависимости этапов, настройки, НСИ, роли, интеграции, миграцию, тестирование, обучение и порядок приёмки.

## Правила доказательности

- Точные имена объектов, полей, форм, команд и регистров брать только из подтверждённых L3-узлов.
- Поведение и пользовательский порядок опирать на L4, типизированный путь графа или явное решение пользователя.
- Не превращать `candidate`, `assumption` или `gap` в факт.
- В подтверждённых шагах не использовать `candidate`, `unresolved`, inferred или предположение модели. Такие сведения выносить в GAP/«требует проверки» и не давать как команду пользователю.
- Если подтверждённая модель допускает альтернативы, показать ветви и условия, а не выбирать вариант молча.
- Сохранять точные graph IDs в секции трассировки, но не перегружать ими основные шаги.

## Сохранение

`run_api_agent` автоматически выполняет сохранение с:

- `kind="answer"`;
- осмысленным `title`;
- полным Markdown в `content`;
- `metadata` с типом ответа и использованными ревизиями артефактов.
- `provenance` фактического API-провайдера, модели и версии skill.

MCP отклонит сохранение без design approval или при неверном provenance. Ответ после сохранения имеет статус `feedback_pending`, а не successful. Затем вызвать `validate_project(for_final=true)` и исправить найденные ошибки без нового широкого исследования.

Показать пользователю Markdown и точный путь `answers_md/...`, запросить отдельное финальное подтверждение. Закрыть project query как `needs_input`; агентный run уже закрыт инструментом. Только по фактическому «подтверждаю итоговую инструкцию» вызвать `record_project_approval(stage="final", approved=true)`. MCP самостоятельно повторит Modeler и только тогда присвоит `successful` и обновит реестр подтверждённых примеров. При замечаниях вызвать final approval с `approved=false`, сохранить контекст и вернуть проект в моделирование затронутых требований.
